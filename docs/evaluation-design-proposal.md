## 評価で学んでほしいこと

部品の役割と基本的な使い方を理解し、利用者の目的・条件に合わせて構成を選び、得られることと負担を説明できるようにする。実サービスと同じ部品を置くことや、すべての特性を最大化することを正解にしない。

## 3つの結果を分けて表示する

| 結果 | 確認すること | 表示案 |
| --- | --- | --- |
| 学習の到達度 | 部品の役割、接続の意味、操作した結果、選択理由を理解したか | ステージ進捗・できたこと・次の練習 |
| 必須条件への適合 | 機能が成立するか、必須の安全性・保存・予算等と矛盾しないか | 設計上の対応方針あり／要修正／未確認 |
| 優先特性への対応 | この課題で重視する特性に対し、根拠のある構成を選べているか | 特性ごとの対応度と重み、条件が揃った場合だけ総合点 |

学習到達度を設計点に混ぜない。教材の操作で確認できたことと、自由設計の説明から判断したこと、実環境で測定したことも区別する。構成図から実際の応答時間・料金・耐久性を算出したとは扱わない。

## 重みの出発点

「SNSならこの配点」ではなく、次の順で決める。

1. 利用者と主要な利用場面を定義する。
2. 通常／ピーク負荷、通信環境、障害の範囲、運用人数、予算を置く。
3. 絶対に守る条件と、優先して良くしたい条件を分ける。
4. 各条件を具体的な場面と目標にし、重みの理由を付ける。
5. 設計・採点の前に利用者へ示し、課題の版として固定する。

「性能を重視する」だけでは採点しない。例えば「指定した回線条件・ピーク負荷で、動画の再生開始を短くする」と「投稿を受け付けてから他の人の一覧へ反映するまでを短くする」は、同じ速度の話でも対象の経路と設計判断が異なる。

一つの条件には主となる採点項目を割り当て、同じ根拠不足を性能・鮮度・拡張性の3項目で重ねて減点しない。別の項目にも影響する場合は、それぞれ異なる要件と影響を説明する。

## 特性の整理

現行の6項目をそのまま重み付けするだけでは、応答性能・鮮度・データの扱いが不足する。特性の語彙を整理し、課題ごとに主に3〜5項目を見せる。

| 特性 | 課題に結び付ける例 |
| --- | --- |
| 応答性能 | 閲覧要求から表示・再生開始まで、指定負荷での処理能力 |
| 情報の鮮度 | 投稿受付から一覧・検索・通知への反映まで |
| 拡張性 | 指定された利用増に対して、能力を増やせる構成と制約 |
| 可用性・復旧性 | 指定の部品が停止したとき、何を続け、何を止め、どう戻すか |
| データの耐久性 | 受け付けた情報を、指定の故障や誤操作からどう守るか |
| 整合性 | どの操作で最新・順序・重複防止が必要か、どのずれを許容するか |
| 安全性・プライバシー | 公開範囲、認証・認可、データへのアクセス境界 |
| 変更・運用のしやすさ | 指定人数で変更、監視、復旧、切り戻しを扱えるか |
| 費用効率 | 見積条件に対する費用と、得られる効果・運用負担 |

情報の鮮度はこの教材で区別するための観点であり、性能や整合性と無関係な普遍的分類だとは主張しない。現行の「実現性」は基本機能の成立確認へ移す。安全性・耐久性などは必須条件にも重点項目にもなり得る。重みに載せない項目を「考慮不要」とはしない。

予算やチーム人数には上限条件としての側面がある。予算上限の遵守と、その範囲での費用効率は分ける。最低条件を満たしただけで二重に加点しない。

## SNSの教材用比較例

**以下は架空の学習課題の配点案であり、InstagramやXの社内基準・実際の配点ではない。** 会社名だけで採点条件を決めず、同じサービス内でも写真一覧、動画、DM、速報、検索を分ける。

- 写真・動画共有: 弱い回線でも閲覧・再生が滑らかなことを優先。投稿反映は教材で指定する一定の遅れを許容し、保存・配信コストも意識する。
- 速報・会話: 出来事の最中に投稿と会話が素早く反映されること、急な集中アクセスに対応できることを優先。どのくらいの負荷と遅延を想定するかは課題で固定する。

| 重点項目 | 写真・動画共有 | 速報・会話 |
| --- | ---: | ---: |
| 閲覧時の応答性能 | 35% | 15% |
| 投稿反映の鮮度 | 10% | 35% |
| 集中アクセスに対する拡張性 | 15% | 25% |
| 障害時の利用継続 | 20% | 15% |
| 運用・配信の費用効率 | 20% | 10% |
| 合計 | 100% | 100% |

数値は議論用の提案で、実測や専門家合意から導出した値ではない。先に優先順位と理由を決め、具体例を比較してから数字を調整する。重みの違う課題の総合点を、同じ尺度の成績として順位付けしない。

例えば「最新投稿が早く見える」は、教材上の仮定として「ピーク時にも受付済み投稿の95%を2秒以内にフォロワーの一覧へ反映」という条件に落とす。負荷・回線・対象・除外条件も併せて定義する。この数値は実在サービスのSLOではない。図だけで達成済みとせず、該当経路・設計上の根拠・確認方法を評価する。

## 必須条件は重みで相殺させない

例えば両課題で次を必須とする案が考えられる。実際の対象範囲は課題に明記する。

- 権限のない人に非公開投稿の本文・画像を返さない。
- アプリ1台が停止しても、受付済み投稿を失わない。DB自体の故障や誤削除まで守れると自動的に拡張解釈しない。
- 指定された投稿・閲覧の基本経路が成立する。

明示的な違反があれば「要修正」、判断材料が足りなければ「未確認」。未確認を合格にも欠陥にも変換しない。安さや速度の点数が高くても必須違反を相殺せず、総合点の確定を保留する。

整合性も操作ごとに扱う。「いいね数の反映は遅れてよい」と「非公開化後の権限判定が古くてよい」は別の条件である。SNS全体に一つの整合性方針を機械的に当てはめない。

## 対応度と計算の案

AIが各特性に自由な0〜100点を付ける方式をやめ、各条件について以下の状態と入力中の根拠を返す方式を検討する。

| 状態 | 区別する内容 | 計算への仮の換算 |
| --- | --- | ---: |
| 対応方針に根拠あり | 条件に対応する経路・設定・理由が説明され、既知の矛盾がない | 100 |
| 一部のみ対応 | 対応できる範囲と、対応できない範囲を具体的に特定できる | 50 |
| 明示的な矛盾 | 入力の記述や接続が条件と矛盾する | 0 |
| 未確認 | 判断に必要な説明・条件が不足する | 未採点 |

この換算も未確定。特性ごとの具体例・妥当な別解で判定を揃えてから採用を決める。「一部対応」と「情報不足」を区別できる例を用意する。実環境で試験したかは別の証拠状態として示し、学習用の設計案に未実施の本番試験を一律要求しない。

重み合計は100。必須条件に未確認・違反がなく、重み対象がすべて評価可能になったときだけ、サーバーで`Σ（重み × 対応度）/100`を計算する。未確認を0点として加算したり、未確認の重みを分母から外して高得点に見せたりしない。途中は「評価可能な範囲60%・未確認40%」と必要な説明を示す。

学習者に求めるのは文字数ではなく、条件・部品・接続・選択理由の対応。説明が短くても同じ内容なら同じ判定を目指す。特定の部品・製品の採用だけを加点しない。

## 誰が基準を決めるか

- 用意した課題: 課題作者が目的・必須条件・重み・理由を固定し、設計前に利用者が確認できるようにする。ヒアリングで条件を段階的に知る場合も、採点前に未確認条件を整理できるようにする。
- 自由課題: 利用者が明示的な課題設定で目的・条件・優先度を置く。これは学習用の自己設定課題として表示する。
- AI: 固定された条件に対して入力の根拠・不足・矛盾を指摘する。採点中に重み・必須条件・合格条件を変更しない。
- アプリ: 設定の値と版、条件ID・部品ID、計算・表示状態を検証する。会話や部品説明に書かれた変更指示は課題設定を変更しない。

自由課題の正式設定を受け取るデータ契約と、現在のサーバー固定要件との関係は実装前に設計する。今回、その境界・保存形式・公開APIを変更しない。

条件や重みを変えた場合は別の版として評価し、以前の結果に使った設定を保持する。会話から根拠付きの仕様案を作り、確認・検証後に確定仕様として設計と採点へ渡す。AIの回答や会話中の「合意済み」を、確認なしの設定変更にはしない。条件そのものは部品説明へ書き写す必要をなくし、部品等の記録は設計上の対応方針や理由を補足するために使う。

## 学習体験へのつなぎ方

入門は1つの部品・少数の特性から始める。部品の役割、接続、操作した結果を確認し、その後「キャッシュは速いが古い値が残る」などのトレードオフを体験する。習った特性を段階的に増やして、卒業課題で目的に合う選択と理由を説明する。

同じ図を「写真・動画共有」と「速報・会話」の2条件で比較し、どの要件・重みが結果を変えたかを見せる。部品を増やせば点数が上がる体験を避け、必要なところに複雑さや費用を使う意味を学ぶ。経験者は条件と重点特性を確認して自由設計へ進める。
