# カスタム課題の進め方

カスタム課題は、テーマだけを決めて聞き取りから条件を発見する方法と、利用者が仕様を決めてから設計する方法を分ける。両者に同じ「隠れた正解」を当てはめない。

## 条件をおまかせ

利用者はテーマ、サービスの型、複雑さ、聞き取り相手を選ぶ。サービスの型は社内業務、コンテンツ、リアルタイム、取引の4種類、複雑さは基礎、標準、応用の3段階で、組み合わせは12通りある。

具体的な利用者数、集中時の負荷、応答、保存、故障、権限、運用条件はバックエンドが持つ。フロントエンドには詳細条件を含めず、開始時に選んだ型と複雑さを保存する。会話と評価は同じ選択から同じ条件を組み立てるため、途中保存、JSON保存、共有、再開の後にも課題条件が変わらない。

AIは依頼者として回答する。学習者は質問によって条件を明らかにし、その条件を根拠に構成を考える。

## 自分で仕様を決める

利用者はテーマと、すでに分かっている仕様を書く。バックエンドは別の隠れた条件を追加しない。AIは依頼者ではなく整理役となり、書かれていない条件について質問し、利用者が決めた内容を整理する。評価では未記載の項目を欠陥と断定せず、仕様未定として扱う。

この方法では、自由記述を構造化した確定仕様や合意履歴へ自動変換していない。隠れた条件がないため、既定課題や「条件をおまかせ」で使う聞き取り到達度の母数も設けない。

## 聞き取り到達度

既定課題と「条件をおまかせ」では、各AI回答が、その回答本文で具体的に明らかにした条件IDを返す。ブラウザは条件ID、表示名、質問、回答、会話内の位置を一組で保存する。評価時にバックエンドの全条件と照合し、「会話で確認できた条件」と「まだ確認していない条件」を設計スコアとは別に表示する。

条件を聞けたこと自体は、設計が条件を満たした証拠にはしない。設計点は構成図と設計理由から判定する。自由メモや会話全体は評価へ送らず、確認済み条件の根拠となる質問と回答だけを送る。

現在の記録はブラウザで編集できる学習用データであり、正式試験の不正防止には使えない。また、条件の交渉による変更、回答側AIの矛盾、合意した仕様の版管理は未実装である。

## データと互換性

- 新しいカスタム課題は `customMode` を保存する。
- 条件をおまかせする場合だけ `scenarioFamily` と `difficulty` を保存する。
- 自分で仕様を決める場合は `scenarioFamily` と `difficulty` を持たない。
- 以前のカスタム課題は従来どおり読み込める。
- 新しい項目を含む保存データは schema version 3として扱う。
- 不正な組み合わせはフロントエンドの読み込み時とバックエンドの要求検証時の両方で拒否する。

保存ファイルは利用者が編集できるため、正式な試験の改ざん防止には使えない。このアプリでは、同じ練習を保存・共有・再開できることを目的にする。

## 今回の確認範囲

- 2方式の開始フローとスマホ表示
- 保存、JSON、共有リンクの往復
- 旧カスタム課題との互換性
- 12通りのサーバー条件の選択
- 会話と評価への同じ条件の引き渡し
- 条件IDと根拠となる質問・回答の保存、全条件との照合
- 聞き取り到達度と設計スコアを分離した表示
- 自分で仕様を決める方式で隠れた条件を作らないこと
- 不正な項目の組み合わせをAI通信前に拒否すること

ローカルの固定AI応答を使った自動テストまで実施した。Gemini実APIでの会話品質と、初学者が2方式を迷わず選べるかは未確認である。
