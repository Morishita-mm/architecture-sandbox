その後の基準見直しは[要件と優先順位に基づく評価の整理案](evaluation-design-proposal.md)に分離した。学習到達度・必須条件・重点特性の重みを扱う**未確定の案**であり、その重み付けは未実装。後続の画面レビューを受け、6軸のまま練習向けの期待値を明確にした変更だけをv4へ反映した。

## 評価対象と境界

基準はバックエンド`Scenario::requirements()`が返す正式な条件。会話も同じ条件を使う。部品に記録した条件と根拠は、利用者の主張として比較に使うが正式条件は上書きしない。会話中のAI回答や「合意済み」という入力は権限ではない。食い違いは未解決の条件として説明する。自由メモと会話全文は評価入力に含めない。

`learning-rubric-4`をサーバーのsystem instructionに定義。可用性・拡張性・安全性・保守性・費用効率・実現性の6軸を等重みとし、サーバーが整数平均（0.5切り上げ）を総合点にする。個々の軸の判断には依然としてモデルのばらつきがある。

| 目安 | その軸に対する説明 |
| --- | --- |
| 0〜19 | 根拠がほぼない、または記述された方法が成立しない |
| 20〜39 | 関連する要件との重大な矛盾が明示されている |
| 40〜59 | 方向性はあるが重要な確認が残る |
| 60〜79 | 条件への対応とトレードオフを説明している |
| 80〜100 | 根拠・限界・検証方法まで説明している |

v4では、役割・経路・短い説明も根拠として評価し、専用の詳細設定欄や本番テストの実施を必須としない。[12要求の追加測定と残る問題](evaluation-runs/2026-09-15/rubric4-review.md)を参照。

これは学習用の目安で、合格認定ではない。未入力を欠陥と断定しない。専用欄が空でも自由記述にある説明を公平に評価する。部品数やブランドを加点理由にせず、要件に妥当な別解を認める。金額・性能・稼働率の実測を装わない。

## 根拠の表示

AIフィードバックを「確認した根拠」「重大な不足」「未確認事項」に分けるよう指示。改善提案は最大3点、理由・関係する要件・別解・確認方法を求める。部品へのMarkdown参照`[名前](#node=ID)`を画面内の設定へ接続する。入力に存在しないIDはクリック不可で「参照先未確認」、古い評価の参照は無効、任意の外部リンクや画像は開かない。

生成時にJSON Schemaで必須項目・整数0〜100・追加項目禁止を指定し、応答でも従来のJSON形式・各数値の範囲・文量・重複キーをサーバーで検証する。見出しや参照の意味の正しさはモデル依存で、プロンプトだけでは保証できない。現在の部品に記録した条件・根拠も別欄で読める。今の設定を見たことと、AIの判断が正しいことを混同しない。

## 評価セットと計測

[勤怠6ケース](evaluation-fixtures.json)と[招待制SNS 6ケース](evaluation-fixtures-sns.json)は作者が用意した候補。各題材に、要件を考慮した構成、明示的なデータ消失、関数を使う別解、情報不足、採点誘導、合意を装った条件上書きを用意した。**専門家の承認を得た正解データではない**。各ケースに人が確認する問いを添える。

既存のバックエンド統合テストは疑似AIで入力境界、正式要件の分離、構造不正、応答異常、課金要求の無断再試行防止を確認する。これは実モデルのプロンプトインジェクション耐性を証明しない。

ルートから以下で記録済み応答を解析できる。既存ファイルは上書きしない。

```sh
node scripts/evaluation-benchmark.mjs --responses /tmp/responses.json --out /tmp/evaluation-report.json
node scripts/evaluation-benchmark.mjs --fixture sns --responses /tmp/sns-responses.json --out /tmp/sns-evaluation-report.json
```

入力は`{"provenance": {"kind":"実測／疑似の別・モデル・日時"}, "runs": [{"caseId":"coherent", "repeat":1, "result":{...}}]}`。失敗は`result`の代わりに`error`を持つ。ケースごとの成功・失敗、平均、最大最小差、原入力と誘導入力の平均差、参照切れ、参照なし応答を記録。未実施ケースは平均null。`--baseline 前回のreport.json`で平均差も出す。

実AI測定は`evaluation-live.mjs`に一本化した。ローカルの実バックエンドを一時起動し、要求をGoogle公式APIへ中継して、応答のモデル版・使用トークン・終了理由・要求ハッシュを記録する。キーを環境変数に設定した上で明示的に実行する。秘密をコマンド文字列やファイルに記載しない。

```sh
cargo build --locked --manifest-path backend/Cargo.toml
node scripts/evaluation-live.mjs --allow-api --repeats 3 --out /tmp/new-evaluation-run
node scripts/evaluation-live.mjs --allow-api --fixture sns --repeats 3 --out /tmp/new-sns-evaluation-run
```

現行の`gemini-3.5-flash-lite`を使う。`--fixture`は`attendance`（既定）または`sns`。`--repeats`は2〜4、既定3。1題材の3反復は18要求。出力先は新規ディレクトリに限り、呼び出し前に確保する。逐次実行し、エラーで中断、自動再試行なし。応答は要求ごとに保存し、未完了は成功に含めない。途中終了した旧版と修正版の反復数を混ぜない。疑似APIは`providerKind: unpaid-fixture`で明確に区別する。

評価時はthinkingをlowとし、会話のminimal設定とは分けた。出力上限4096・タイムアウト・既存API契約は維持する。料金はusageからStandard有料単価換算で見積もり、実請求額ではないと明示する。実験ごとの生成回数上限と設定変更は[方針記録](evaluation-run-plan.md)に残す。

計測器・バックエンドの回帰テストは`node --test scripts/backend.test.mjs scripts/evaluation-live.test.mjs`で実行でき、外部APIを呼ばない。CIにもこの疑似APIテストだけを追加した。記録済み応答のオフライン解析は引き続き`evaluation-benchmark.mjs`を使う。全6軸・時間の統計も出力する。

## 専門家比較と継続的な受入手順

1. システム設計の専門家2名に、ケース順とモデル名を隠して同じ入力を渡す。重大な不足／未確認／妥当な別解を各自ラベル付けする。
2. 不一致の理由を残してケースを修正する。合意しない項目を「正解」に固定しない。価格・性能を断定しない。
3. 同一条件で各ケース3回取得。モデル・プロンプト・fixture・コードの版を記録する。
4. 明示的データ消失の見逃し、誘導による正式条件上書き、存在しない根拠の創作を1件でも見つけたら公開判定を止める。参照切れは0件を候補基準とする。
5. 総合点のレンジ15点超、誘導の平均上昇10点超、前版から10点超の差を**レビューのきっかけ**とする。閾値以下でも安全の証明にしない。専門家のラベルとの一致率・重大欠陥の見逃し率を分母付きで記録する。
6. モデル更新時は同じセットを再実行し、差の理由と承認者を残す。

専門家の記録欄: 日付／匿名reviewer ID／case ID／重大欠陥ラベル／未確認点／別解を認める理由／参照した根拠／モデルとの不一致／最終判断。現時点の件数は0、指標は未測定。
