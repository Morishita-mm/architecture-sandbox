# Architecture Sandbox リデザイン方針

## 目的と前提

システム設計を練習するエンジニアを主な利用者と想定し、シナリオ選択 → ヒアリング → 構成図 → 評価の流れを、統一した見た目と明確な操作の優先順位で支える。

現行画面には、青・緑・黄が大きな面に使われ、ボタンやカードの影・角丸・文字サイズも画面ごとに異なる。これは現行コードとローカル画面の観察に基づく整理で、ユーザー調査による評価ではない。「モダン」を色の変更だけで実現せず、文字、余白、構造、操作状態を一緒に整える。

## ローカル比較

Vite開発サーバーで `/design-lab.html` を開く。上部のA/B/Cとアプリ内ナビゲーションで、同じデータの4画面を比較できる。URLの `concept` と `view` から直接開くこともできる。

| 案 | 意図・構成 | このアプリへの適性 | 留意点 |
| --- | --- | --- | --- |
| **A / Precision（推奨）** | 白・グレー・少量の青、細い罫線。名前付きのサイドバー、中央の作業面、右の補助情報。 | 長い日本語の会話と構成図を同じルールで扱いやすい。現行機能の移行も段階的に進められる。 | 控えめなので、ブランドらしさは言葉・図形・細部で補う。 |
| **B / Midnight** | 墨色のレイヤーとライム。コンパクトな操作レールで作業面を広くする。 | 開発ツールとしての個性が強く、図の編集に集中しやすい。 | 名前を隠した操作の発見しやすさ、補助文字のコントラスト、長文の読みやすさを確認する。 |
| **C / Atelier** | 温かい紙色とピーチ、セリフの見出し、上部ナビゲーション。 | 初めての設計や、学びの振り返りを親しみやすく見せられる。 | 余白の多さと大きな構成図の密度を両立させる必要がある。 |

推奨はAを基礎とし、色・余白・文字・角丸の共通ルールを先に導入する方向。Bはダークテーマの候補、Cはトップ画面・操作ガイド・振り返りの雰囲気を検討する比較軸になる。採用案は未決定。

## 共通の設計原則

1. **一画面、一つの主役。** ヒアリングは会話、設計は構成図、評価は改善点が主役。補助情報を右側にまとめ、構成図の上をプロパティで覆わない。
2. **色に役割を与える。** 操作、選択、コンポーネント種別、成功・警告・削除の意味を混在させない。状態は色だけに依存せず、ラベルやアイコンも添える。
3. **図と文章に場所を譲る。** 大きな影や文字の装飾を減らし、文字サイズ・行間・罫線・余白で構造を伝える。編集画面では装飾的な見出しを控えめにする。
4. **操作を見える場所に。** コンポーネント追加・削除・詳細編集、送信と改行の違いを明示する。キーボードフォーカスも視覚化する。
5. **広さに合わせて配置する。** デスクトップは複数ペイン、狭い画面は補助情報を下段へ。細い画面にデスクトップの密度をそのまま縮小しない。

## 参考と解釈

- [Refero / Dub](https://styles.refero.design/style/b0d80806-b724-4ed1-a1d1-074edd3c9bc9)：明るい面、細い罫線、限られたブルー、控えめな影をAの参考とした。
- [Refero / Linear](https://styles.refero.design/style/90ce5883-bb24-4466-93f7-801cd617b0d1)：暗い面の段階と単一の明るいアクセント、精密な形状をBの参考とした。
- [Refero / Steep](https://styles.refero.design/style/75fdb89f-ca64-41b3-af36-7a78bd09448e)：セリフの見出し、温かいアクセント、静かなカード表現をCの参考とした。

参照日は2026-09-13。Refero掲載のWebサイト由来のスタイル資料から原則を抽出したもので、各社の実際のアプリUIや内部デザインシステムをそのまま再現したものではない。資料中のマーケティング向けの大きな余白や見出しは、編集画面には直接持ち込んでいない。

## 今回のプロトタイプ範囲

- 各案でシナリオ、ヒアリング、構成図、評価を表示。
- シナリオ選択、デモチャット、メモ編集、コンポーネント検索・追加・削除・移動・接続・名前編集、ペイン切り替え、参考資料ダイアログを操作可能。
- AI応答・要件・スコアはデザイン比較用サンプル。外部AIへの送信、実評価、自動要件抽出、保存機能は実装していない。要件ノートの構造化表示は提案であり、現行機能としては扱わない。
- リロードするとサンプル状態に戻る。フリーテーマ選択も比較画面への遷移のみで、実際のシナリオ定義は現行版を使う。
- 既存アプリとは別のHTMLエントリーを使用。既存の `index.html` と本番用ビルド設定を変えず、開発サーバーでだけ配信する。本番ビルドにデザイン比較ページを追加しない。

## 比較の観点と本実装への進め方

同じシナリオの4画面を各案で見比べ、「会話が読みやすいか」「次の操作が見つかるか」「図を広く使えるか」「評価から改善へ戻りやすいか」で選ぶ。レビュー中は色の好みと操作上の問題を区別して記録する。

案の選択後、共通トークン・基本部品 → ヒアリングと構成図 → シナリオ選択と評価の順で移行する。データ保存形式、API、コンポーネント削除、Shift + Enter、1〜3行の入力欄、送信中のタブ移動を保つ。実装時には通常・空・選択・読み込み・失敗・フォーカスの各状態と、代表的な画面幅で検証する。

## 検証記録（2026-09-13）

- 3案 × 4画面をデスクトップと幅390pxで確認。画面幅を超える横スクロールは発生しない。検証後はビューポート設定を解除。
- デモチャットの複数行送信、部品の追加・名前編集・削除、端子同士の接続、画面遷移、参考ダイアログの開閉をブラウザで確認。
- ESLint、TypeScriptを含む本番ビルド、単体テスト34件、既存アプリのE2Eテスト13件、Cloudflare dry-runが成功。デプロイは行っていない。
- 本番ビルドに `design-lab.html` が含まれないことを確認。E2Eは既存アプリの回帰確認であり、比較ページ自体の自動テストではない。
- 開発画面ではReact Flow 11の型定義オブジェクトに関する警告が表示される場合がある。`nodeTypes` はモジュールスコープに固定済みで、ライブラリの開発用チェックとStrictModeの二重実行によるもの。操作に影響する実行エラーは確認していない。

残る判断は採用方向の選択。本番UIへの移行と実際のAI・評価処理への接続は、案のレビュー後に進める。
