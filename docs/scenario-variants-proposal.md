# 固定シナリオの詳細設定案：勤怠3パターン・画像SNS3パターン

2026-09-16 / [Issue #19](https://github.com/Morishita-mm/architecture-sandbox/issues/19)。[出題条件・聞き取り・評価の方針](interview-evaluation-proposal.md)を具体化する6案。**架空の教材用条件であり、実装済みの初期値と配点である。専門家による妥当性確認は未実施。** 保存期間は法令の解説ではなく、この教材の発注者が求める値。予算は希望するインフラ利用費で、実際のクラウド料金の見積もりではない。

現行の `internal_tool` と `sns_app` の中で選ぶケースを想定し、規模だけで難易度を変えない。人数が少なくても、オフラインや素早い情報反映などの条件で別の判断を学べる。

## 共通の扱い

- 表の値をそのケースの開始時に固定する。会話中に再抽選しない。交渉は各ケースに明記した範囲のみを初期案とし、理由・合意・基準の新しい版を記録する。
- 「発注者の最初の説明」は課題文でも提示できる。表の詳細は発注者役が持ち、関連する質問に答える。特定のキーワードを言わないと開示されない設計にしない。
- 秒数の目標は、指定したピークを含む健全時に成功した操作の95%が満たす目標。失敗は別に扱い、故障時の条件は各表で示す。指定の操作量を処理できる方針が必要で、要求を常に拒否して応答時間だけ達成する構成は認めない。教材の標準回線は下り20 Mbps・上り10 Mbps・往復100 msとする。
- 打刻・一覧の応答は操作から結果を受け取るまで。画像SNSの投稿受付はアップロード完了後から測り、画像の転送と変換の完了を混同しない。投稿を一覧へ反映する時間は受付完了から測る。
- SNSは1投稿1画像、元画像は平均2 MB。一覧1回は200 KBのサムネイル10枚、計2 MB。MB・GB・TBは10進単位。元画像の見積もりにサムネイル・複製・バックアップを含めない。
- SNSの一覧更新回数は利用者の操作量。配信方式によってバックエンドへの要求数は変わる。画像取得を含まない一覧操作数から、DBや画像配信の負荷をそのまま同一視しない。
- 予算は月額の目標で、計算・保存・配信・監視・バックアップを含み、人件費と初期開発費を除く。価格データを持たない初期版は、費用に配慮した方針を診断し、実金額への適合は断定しない。
- 必須条件への対応と、重点特性の重みを分ける。表で交渉対象にしていない条件を、会話AIが勝手に緩和しない。図で判定できない数値は未実証とし、部品の名前だけで達成扱いにしない。

## 社内勤怠管理システム

### A：50人の会社で、無理なく運用する

ケース案ID: `attendance-office`。入門向け。発注者の最初の説明は「50人の会社です。紙の出退勤記録を置き換えたいです。専任のIT担当はいません」。

| 項目 | 発注者が持つ条件 |
| --- | --- |
| 利用者・操作 | 社員50人。出勤・退勤の2回で、最大100打刻／営業日。社員が自分の記録を確認し、人事が月次CSVを出す |
| 集中する場面 | 40人が始業前の5分間に出勤。最も重なる1秒でも5打刻を想定。平均は40÷300≒0.13件／秒で、最大値とは区別 |
| 応答 | 打刻の受付結果を2秒以内に返す。月次CSVは依頼から5分以内でよい |
| 利用時間・故障 | 平日9〜18時を優先。アプリ1台が止まったら営業時間中は1時間以内に復旧。予定した夜間メンテナンスは1回30分まで許容。営業時間外の故障は次の営業日9時までに復旧 |
| 記録の保全【必須】 | 3年保存。保存できたことを確認して受付完了にする。受付済みの記録はアプリ1台の停止で失わない |
| 閲覧・訂正【必須】 | 社員は自分の記録、人事2人は全員の記録を閲覧可能。訂正前の値と、誰が訂正したかを残す |
| 予算・運用 | 月1万円を目標。管理する人は兼任1人、定常作業は週1時間以内を希望 |

**聞き込みの焦点:** 「夜中も使いますか」「停止より、記録が消えることの方が困りますか」「誰が他の社員の記録を見ますか」「運用できる人はいますか」。50人という提示済み情報の聞き直しは不要。

**交渉できること:** 運用負担を減らせる説明があれば月2万円まで。月次CSVは事前予約して翌営業日までに出す方式でもよい。権限と記録の保全は緩めない。

**評価したい判断:** ブラウザ→アプリ→記録を保存する場所、という役割が成立し、少人数で維持できる理由があるか。管理されたサービスにまとめる別解も認める。ロードバランサーやキャッシュの設置は必須にしない。

### B：工場の交代時に、打刻が一斉に集中する

ケース案ID: `attendance-shift`。中級向け。最初の説明は「3,000人が働く工場です。交代時の打刻に列ができるのをなくしたいです。工場は24時間動きます」。

| 項目 | 発注者が持つ条件 |
| --- | --- |
| 利用者・操作 | 社員3,000人。休憩を含めて最大4回、計12,000打刻／日。責任者が部署別の記録を確認する |
| 集中する場面 | 大きい交代では2,400人が2分間で打刻。平均20件／秒、最も重なる1秒は100件／秒を想定 |
| 応答 | 打刻の受付結果を1秒以内に返す。日次集計は翌朝6時まででよく、打刻と同時に完成する必要はない |
| 利用時間・故障【必須】 | 24時間利用。アプリ1台が停止しても、60秒以内に打刻受付を再開できる。応答がなかった操作は再試行できる |
| 記録の保全【必須】 | 3年保存。受付済みの打刻をアプリ1台の停止で失わない。単に端末内に置いただけでは受付完了にしない |
| 正しさ・閲覧【必須】 | 応答が遅くて同じ操作を送り直しても1件として記録する。責任者は担当部署、人事は全体を閲覧可能 |
| 予算・運用 | 月20万円を目標。運用担当2人。深夜に手作業で台数調整する運用は避けたい |

**聞き込みの焦点:** 「平均ではなく、何分間に何人来ますか」「送ったあと返事がなかったら、押し直しますか」「集計はいつまでに必要ですか」「1台止まったら何秒くらい待てますか」。

**交渉できること:** 打刻とは独立して処理するなら日次集計は翌朝8時まで延長可能。故障対応と運用負担を改善する理由があれば月30万円まで。受付済み記録の消失・二重記録は許容しない。

**評価したい判断:** 集中時と故障時の受付経路、再送による重複防止、急がない集計との切り分けを説明できるか。100件／秒だから大規模な分散構成が必要だとは決めつけない。必要な能力と冗長化の目的を区別する。

### C：訪問先で電波が切れても、出退勤を記録する

ケース案ID: `attendance-field`。応用向け。最初の説明は「訪問業務の社員500人が使います。電波が入らない場所でも打刻を残し、あとで本部へ送りたいです」。

| 項目 | 発注者が持つ条件 |
| --- | --- |
| 利用者・操作 | 社員500人、最大4回で2,000打刻／日。20拠点の責任者と人事が確認する |
| 通信の条件【必須】 | 現場の回線切断または中央アプリの停止が30分続いても、事前にログインした同じ端末で打刻を仮保存できる。端末の破損・紛失はこのケースの保証対象外 |
| 応答・同期 | オンラインの受付結果は2秒以内。オフラインの仮保存結果は1秒以内。回線・中央アプリの復旧後、画面が開いている場合は5分以内に同期。閉じていた場合は次回起動から5分以内 |
| 復旧時の集中 | 500台が各4件を持つ場合、計2,000件を5分以内に送る。平均約6.7件／秒。初期の集中は1秒あたり50件を受け付ける前提で、再送間隔を分散してよい |
| 正しさ【必須】 | 「端末に仮保存」と「サーバーが受付完了」を区別。再送で二重計上しない。打刻した時刻とサーバーへ届いた時刻を区別し、訂正履歴を残す |
| 保存・閲覧【必須】 | サーバーで受付済みの記録を3年保存し、アプリ1台の停止で失わない。社員は自分、責任者は担当拠点、人事は全体。端末の仮保存も通常のアプリ再起動で消さない方針が必要 |
| 予算・運用 | 月5万円を目標。運用担当2人。本部が確認する日次集計は翌日でもよい |

**聞き込みの焦点:** 「つながらない間も記録しますか」「保存できたと画面に出た時点で本部も受け取っていますか」「端末の時計が違ったり、同じ記録を送り直したりしたらどうしますか」。時計の信頼性については、疑わしい記録を人事が確認できればよく、端末だけで正確さを保証することは求めない。

**交渉できること:** 本部に未同期の状態を示せるなら、同期期限を15分まで延長可能。端末の仮保存や同期を扱う運用負担を減らせるなら月8万円まで。仮保存を中央の受付完了と見せる変更は認めない。

**評価したい判断:** ブラウザ／端末が持つ記録とサーバーの記録を分け、回復後の同期・再送・状態表示を説明できるか。サーバー側へキューを置くだけでは、端末からサーバーまでの回線切断を解決しないことに気づけるか。

## 画像投稿SNS

### A：招待した仲間だけで、写真を共有する

ケース案ID: `sns-private-community`。入門向け。最初の説明は「会員だけで活動写真を共有したいです。1日1,000人ほど使います。外部の人には写真を見せません」。

| 項目 | 発注者が持つ条件 |
| --- | --- |
| 規模・操作 | 1,000 DAU（1日に使う人数）、100投稿／日。一覧を1人10回開くため10,000回／日、サムネイルは100,000枚分／日 |
| 集中する場面 | 活動終了後の5分間は一覧更新20回／秒。計6,000回で1日の想定内。投稿は最も重なる1秒で2件 |
| 応答・鮮度 | 一覧データは1秒以内、先頭のサムネイル10枚は3秒以内。投稿の受付はアップロード完了後2秒以内。他の会員の一覧への反映は60秒以内でよい |
| 保存・故障【必須】 | 元画像と投稿を1年保存。受付済み投稿をアプリ1台の停止で失わない。アプリの故障は担当者が対応できる8〜20時なら2時間以内、時間外は翌朝10時までに復旧してよい |
| 公開範囲【必須】 | 招待された会員だけが閲覧・投稿できる。画像のURLを知っている非会員にも画像を返さない。会員資格を外したら新しい取得を拒否する。既に端末へ保存された画像の回収は対象外 |
| 投稿者の操作 | 自分の投稿を削除できる。削除操作後は新しい閲覧要求に内容を返さない。保管領域からの物理削除は24時間以内でよい |
| 予算・運用 | 月2万円を目標。兼任1人で運用。動画・DM・推薦アルゴリズムは最初の範囲に含めない |

**聞き込みの焦点:** 「誰が写真を見られますか」「退会した人や、URLを教えてもらった人も見られますか」「すぐに一覧へ出る必要がありますか」「写真はいつまで残しますか」。

**交渉できること:** 保存費を減らす理由があれば、元画像の保存は1年から90日へ短縮可能（このケースでは投稿自体も同じ期間で消える）。運用負担を減らせるなら月3万円まで。会員外への公開は認めない。

**評価したい判断:** 会員確認、投稿の記録、画像の保存、閲覧の経路が成立し、画像だけ別の公開経路から漏れないか。費用と手間に見合う構成か。小規模な構成でも、権限境界を説明できれば評価する。

### B：世界中から、写真を気持ちよく閲覧する

ケース案ID: `sns-photo-discovery`。中級〜応用向け。最初の説明は「世界中の100万人が毎日写真を見ます。投稿してすぐ広まることより、写真を待たずに見られることを重視します」。現行SNSの100万DAU・世界向けという規模を引き継ぐ案。

| 項目 | 発注者が持つ条件 |
| --- | --- |
| 規模・操作 | 100万DAU、10万投稿／日。一覧を1人10回開くため1,000万回／日、サムネイルは1億枚分／日。利用者は日本40%・北米30%・欧州30% |
| 集中する場面 | 15分間は一覧更新2,000回／秒（180万回）。同じ期間の投稿は60件／秒（54,000件）。どちらも1日の想定内 |
| 応答・鮮度 | 各対象地域で一覧データは1秒以内、先頭のサムネイル10枚は2秒以内。投稿受付はアップロード完了後2秒以内。一覧へ反映するまで30秒、いいね数は60秒の遅れを許容 |
| 保存 | 元画像と投稿は1年保存。画像を小さくした閲覧用データを別に持ってよい。元画像だけで約73 TB／年 |
| 故障時【必須】 | 24時間利用。アプリ1台が止まっても、再試行や利用可能な処理先への切替で60秒以内に閲覧を再開できる。受付済み投稿をその故障で失わない。地域全体の停止は初期の必須条件に含めない |
| 公開・削除【必須】 | 投稿は公開。投稿・削除は本人だけ。削除後60秒以内に一覧と画像配信で新しい閲覧を拒否する。既にダウンロードしたコピーは回収対象外。ここでは非公開投稿を扱わない |
| 予算・運用 | 月3,000万円を目標。運用担当6人。ランキングは日次更新でよく、推薦AIや動画配信は対象外 |

**聞き込みの焦点:** 「投稿と閲覧のどちらが多いですか」「どの地域から使いますか」「原寸の写真を毎回表示しますか」「新しい投稿やいいね数は、何秒くらい遅れてよいですか」。

**交渉できること:** 品質への影響を説明すれば、一覧用画像を200 KBから100 KBへ軽量化できる。元画像の保存を1年から180日へ短縮する場合は投稿も同じ期間で消えると合意する。一覧反映は60秒まで延長可能。閲覧開始2秒と投稿者の権限は維持する。

**評価したい判断:** 閲覧向け画像、利用者に近い配信、更新頻度に合うキャッシュ、受付と画像処理の分離を検討できるか。これらは説明の方向であり、CDNなど特定の名前の部品を置くだけで加点しない。キャッシュを使うなら削除と更新の伝わり方も扱う。

### C：イベント中の写真とコメントを、すぐ届ける

ケース案ID: `sns-live-event`。応用向け。最初の説明は「イベント中の写真と短いコメントを共有します。参加者は1日10万人。発表直後に一気にアクセスされるので、古い一覧のままだと困ります」。

| 項目 | 発注者が持つ条件 |
| --- | --- |
| 規模・操作 | 10万DAU、2万投稿／日。1人20回の一覧更新で200万回／日、サムネイルは2,000万枚分／日。対象地域は日本 |
| 集中する場面 | 発表直後の1分間に一覧更新20,000回／秒（120万回）、投稿100件／秒（6,000件）。利用者数はBより少ないが、瞬間的な一覧更新は多い |
| 応答・鮮度 | 一覧データは0.5秒以内、先頭のサムネイル10枚は3秒以内。投稿受付はアップロード完了後1秒以内。受付済み投稿を2秒以内に他の利用者の一覧へ反映。いいね数は30秒遅れてよい |
| 保存 | 元画像と投稿は30日保存。期間後は消えることを利用者へ伝える。元画像だけで約1.2 TB／30日 |
| 故障・過負荷【必須】 | アプリ1台の停止時は60秒以内に受付を再開し、受付済み投稿は失わない。処理しきれないときは受付前に待機・再試行を案内し、成功したように見せて捨てない |
| 正しさ・権限【必須】 | 再送しても同じ投稿を二重に作らない。投稿・削除は本人だけ。投稿は公開で、削除は60秒以内に新しい閲覧へ反映。全利用者で完全に同じ並び順にすることは求めない |
| 予算・運用 | 月500万円を目標。運用担当3人、開催時間中は対応できる。イベント外の深夜は予定した1時間のメンテナンスを許容 |

**聞き込みの焦点:** 「普段ではなく発表の瞬間はどのくらい集中しますか」「一覧の反映が何秒遅れると困りますか」「写真の新着といいね数は同じ速さが必要ですか」「送信を押し直したらどうなってほしいですか」。

**交渉できること:** 画像を200 KBから100 KBへ軽量化、いいね数の反映を60秒まで延長、費用増の理由があれば月700万円まで。投稿反映2秒はこのケースの核として維持する。アップロード前の順番待ちは明示すれば許容するが、指定の負荷を全て拒否して達成扱いにはしない。

**評価したい判断:** 最新の投稿を伝える経路と、混雑時の受付・処理・再送を説明できるか。キャッシュの保持時間を長くするだけでは鮮度を満たせない。キューを入れただけで処理能力が増えた扱いにせず、待ち時間と後段の処理も考える。

## 数値の整合性メモ

以下は教材の入力値からの概算。実効容量・実性能・料金の実測ではない。

| ケース | 一覧更新／日 | サムネイル転送量／日 | 元画像の保存量 |
| --- | ---: | ---: | ---: |
| SNS A | 1,000 × 10 = 1万回 | 1万 × 10 × 200 KB = 20 GB | 100 × 2 MB × 365 = 73 GB |
| SNS B | 100万 × 10 = 1,000万回 | 1,000万 × 10 × 200 KB = 20 TB | 10万 × 2 MB × 365 = 73 TB |
| SNS C | 10万 × 20 = 200万回 | 200万 × 10 × 200 KB = 4 TB | 2万 × 2 MB × 30 = 1.2 TB |

転送量は各更新で全10枚を新しく取得する仮定。端末側に同じ画像が残る場合は減り、CDN等が応答する場合はオリジンからの転送量と異なる。元画像表示・再送・APIの本文は含めない。20 Mbpsで2 MBを送る理想的な転送時間は0.8秒で、実際は通信待ち・サーバー処理・描画等が加わる。2秒という目標の達成をこの計算だけで保証しない。

図で何がわかり、説明や検証が何を補うかも区別する。特に勤怠Cは、今の教材にオフライン同期の専用体験がないため、出題前に小さな前提説明か体験を用意する。

## 重点特性の重み案

[既存の9特性の整理案](evaluation-design-proposal.md)を使う。これは6案の違いを比較する初期配点であり、現行の6軸等重みの採点を変更したものではない。割合は教材作者の提案で、外部の標準配点ではない。必須条件は重み0でも診断対象で、未対応を他項目の高得点で相殺しない。

| 特性 | 勤怠A | 勤怠B | 勤怠C | SNS A | SNS B | SNS C |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 応答性能 | 0 | 0 | 0 | 10 | 35 | 10 |
| 情報の鮮度 | 0 | 0 | 0 | 0 | 0 | 35 |
| 拡張性 | 0 | 15 | 0 | 0 | 20 | 25 |
| 可用性・復旧性 | 0 | 30 | 25 | 0 | 10 | 20 |

| 整合性 | 10 | 25 | 30 | 0 | 0 | 10 |
| 安全性・プライバシー | 20 | 0 | 20 | 30 | 0 | 0 |
| 変更・運用のしやすさ | 20 | 10 | 10 | 20 | 0 | 0 |
| 費用効率 | 25 | 0 | 0 | 25 | 25 | 0 |
| 合計 | 100 | 100 | 100 | 100 | 100 | 100 |

勤怠Aは小さく運用しながら記録を守ること、Bは集中と故障、Cは端末と中央の状態の違いを重視する。SNS Aは公開範囲、Bは閲覧時の快適さと配信費、Cは新着の鮮度を重視する。異なる重みの総合点を、そのまま同じ尺度で順位付けしない。レーダーチャートに表示する軸と重みの説明は、採点基準の確定後に調整する。

## この6案で確かめる聞き込みと設計の違い

| 例 | 聞き込みの判定 | 設計の判定例 |
| --- | --- | --- |
| 勤怠Bで再送の条件を聞き、重複防止の理由も説明した | 条件を把握 | 条件への対応方針あり |
| 同条件を聞いたが、再送のたびに新しい打刻を作る設計だった | 条件を把握 | 明示的な矛盾 |
| 同条件は聞かなかったが、設計に重複防止の説明がある | その条件は未確認 | 対応方針あり。聞き込みの成果へは加算しない |
| SNS CでAIが投稿反映「60秒でもよい」と誤回答した | 回答側の不整合。学習者の聞き漏らしにしない | 有効な条件を再確認するまで、該当する採点を保留 |

「重複しないようにします」だけで技術的に実証済みとはしない。ただし初心者にライブラリ設定や試験結果を要求せず、「同じ操作には同じ識別子を付けて、記録済みなら追加しない」などの短い説明を設計方針の根拠として認める。
