## 目的と進め方

IT自体の初学者が、少ない部品で役割を体験してから自由設計へ進み、要件や設計理由を考える体験を通して、アーキテクチャの大切さを理解できるアプリにする。構成の違いが使いやすさ・止まりにくさ・情報の守り方・費用にどう関わるかを学ぶ。AIの指摘は根拠と未確認事項を区別し、学習の成果を検証する。

- 今回はローカルで実装・検証する。本番配置とコードのpushは行わない。
- GitHub Issueとこのチェックリストを同期する。Issue: https://github.com/Morishita-mm/architecture-sandbox/issues/5
- `[x]` は実装と必要な検証が完了した項目。未完了をチェックしない。
- 本番公開・専門家評価・実ユーザー検証は、ローカル実装の完了と分ける。
- 今回のローカル実装では、任意の追加設定と後方互換の移行を採用。公開・実AIの費用を伴う検証・参加者への依頼は、準備と実施を分ける。
- 2026-09-15更新: 対象はIT自体の初学者。学習コースと自由設計の2つの入口を設け、学習では使える部品を段階的に増やす。経験者は最初から全種類を使い、学習完了を設計開始の条件にしない。ライセンスはMIT。以前の自由設計のみの入口方針を更新。学習コースは [Issue #6](https://github.com/Morishita-mm/architecture-sandbox/issues/6) と `docs/learning-course-plan.md` で別途追跡する。

- [x] EDU-08 トップに学ぶ目的と任意の学習ガイドを追加。学習コースの追加後は「設計のヒント」として表示。ガイドに、部品の役割・線で渡すもの・つなぎ方の理由を説明する学習目標、プログラミング不要の前提、最初の10〜15分という練習時間の提案、一区切りの目安を明示。学習目標は青いカードと大見出し、一区切りの目安は緑、前提と時間は灰色の補足欄に整理し、配置と文字サイズでも重要度を示す。必須手順や時間制限を設けず、任意に振り返れる。時間と学習効果の実利用検証はRESEARCH-01。

- [x] EDU-10 手動の学習記録として、要件メモの「要件と設計を記録」から、条件・確認状態・根拠・関連部品・対応方針・変更前後・次に確かめることを一組にして追加できる。確認済みには利用者が根拠を入力する。既存メモは保持し、通常の文字として編集・自動保存・JSON復元できる。閉じても同じ作業中は入力を保持し、容量超過・選択部品の削除も処理する。部品名は記録時点の名前で自動追従しない。メモの自動解析・根拠との自動照合は行わない。EVAL-02 / EVAL-03では、部品の専用欄に明示した条件と根拠を評価に含める。自由メモと会話全文は自動送信しない。

## 4. 設計の表現とデータ契約（ローカル実装）

- [x] MODEL-01 部品の役割・実装方式・管理者を任意入力で分離。既存32部品IDを維持し、新設定のある保存だけschemaVersion 3にする。旧Base64/v2は読め、旧アプリでv3を無言で欠落させない。公開採点DTOは維持し、新設定を既存の部品詳細へ変換する。移行と制限はローカルの`docs/design-model.md`に記録。
- [x] MODEL-02 Security Groupを実線と通信ルールの説明で表示し、新たな自動格納を停止。各部品の設定でSGを明示的に関連付け、SG側で許可通信を記録する。旧囲みは位置と内容を維持し、関連付けとは別であることを確認画面に表示。実通信の許可判定はしない。
- [x] MODEL-03 Subnetの所属VPCとAZ、部品の配置Subnet／AZをIDで記録。単一の包含ツリーにせず、参照先の種類・存在・AZ不一致・未指定を確認できる。参照切れでも作業を保存し、設定から選び直せる。図の囲みから所属を推測しない。
- [x] MODEL-04 接続に渡すもの・通信方式・同期／非同期・失敗時の対応を追加。線からも部品の接続一覧からも編集でき、キーボード・Undo/Redo・保存・再開・評価入力に反映。長いラベルで図を覆わず、全文は設定で読める。
- [x] MODEL-05 既存部品の担う仕事としてアプリ・認証・API連携・通知・決済を選択し、内部／外部の管理範囲を分離。図にも外部サービスと役割を表示。外部が応答しない場合の問いを確認画面に用意し、接続へ再試行等を記録できる。
- [x] MODEL-06 台数・実行単位数と、冗長化／切替・バックアップ／復元・許容停止時間／データ損失の目標を別項目にした。複数台だけでは可用性の達成と判断せず、接続ごとの再試行も分離。未入力を未確認として扱う。

## 5. AI評価の信頼性（基準の実装と実品質の検証を区別）

- [x] EVAL-01 サーバーに`learning-rubric-3`を定義。6軸を等重みとし、総合点をサーバー側で平均計算。重大な矛盾・未確認・妥当な別解を区別する方針を画面と`docs/evaluation-quality.md`に明示。基準の実装を完了とし、実モデルの遵守率はEVAL-04/05に残す。
- [x] EVAL-02 部品の条件・根拠を利用者の記録として評価入力に含め、AI文中の部品参照から該当設定へ戻れる。存在しない参照や任意の外部リンクを開かず、古い評価の参照は無効化。現在の部品に記録した根拠を別欄で読める。根拠の真偽やAIの意味理解を保証しない。
- [x] EVAL-03 正式条件は従来どおりサーバーを正とする。部品に記録した条件・会話の抜粋は利用者の主張として比較し、「合意済み」という文で正式条件を上書きしない。自由メモと会話全文は自動送信しない。正式な合意管理へ拡張する場合の境界を文書化。

- [x] EVAL-06 「設計を確かめる」に、入力からの事実・未確認・考える問いを分けた確認、部品全体の停止を仮定する有向グラフの到達性、変更前後の部品／接続比較を実装。該当設定への移動と結果のメモ追記が可能。AI通信なし。実性能・実際の切替・データ損失は計算せず、限界を表示。

## 6. 聞き取りとカスタム課題

- [x] INTERVIEW-01 カスタム課題を「条件をおまかせ」と「自分で仕様を決める」に分ける。前者は4つのサービス型と3段階の複雑さからバックエンドの条件を固定し、会話・保存・共有・再開・評価で同じ条件を使う。後者には隠れた条件を設けず、AIを仕様の整理役にする。旧カスタム課題を読み込める。詳細は `docs/custom-scenario-modes.md`。
- [x] INTERVIEW-02 各AI回答が実際に説明した条件IDを構造化して返し、条件ID・質問・回答・会話位置を一組で保存する。JSON保存・再開・評価の鮮度判定へ含め、不一致や不正な参照を拒否する。会話全体と自由メモは評価へ送らない。モデルが本文で条件を開示してIDを落とした場合は、サーバー管理の条件断片で補正する。内部プロンプト・非公開条件の抽出要求はGeminiへ送らず、条件を再掲しない応答にする。
- [x] INTERVIEW-03 バックエンドの全条件と聞き取り記録を照合し、確認済みと未確認を別指標で表示する。聞けたことだけで設計点を加算せず、構成と設計理由への対応を別に評価する。
- [ ] INTERVIEW-04 既定2テーマの各3パターンを、条件ID・聞き込み判定・妥当な別解とともに実装する。現時点は `docs/scenario-variants-proposal.md` の提案までで、アプリの既定課題は従来の固定条件を使う。
- [ ] INTERVIEW-05 交渉で変更した条件、回答側AIの矛盾、合意した仕様の版を区別し、評価が参照した版から根拠へ戻れるようにする。現在の記録は確認済み／未確認の2状態で、正式試験の改ざん防止は行わない。
